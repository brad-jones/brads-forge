# Working with APM (Agent Package Manager)

This repo declares its agent context — instructions, skills, prompts, agents, hooks, MCP servers — in `apm.yml`. Running
`apm install` / `apm compile` resolves that manifest and _writes_ files like `CLAUDE.md`, `AGENTS.md`, and
`.claude/skills/` from it. Those written files are build output, the same way `dist/` is build output for a bundler.
**Edit the source and regenerate; don't hand-edit the output.**

Getting this wrong doesn't just get overwritten later — `apm audit` (often wired into CI) diffs the working tree against
a fresh install/compile and fails the build on any mismatch. A hand-edit you thought was harmless becomes a red CI check
for someone else.

This skill only applies if the repo has an `apm.yml` at its root (or you're asked to add one). If it doesn't, none of
this is relevant.

## The core distinction

|                | Source of truth (edit this) | Generated output (never hand-edit)                                                                                                                                                                     |
| -------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| What it is     | What you _declare_          | What APM _writes_ from the declaration                                                                                                                                                                 |
| Lives in       | `apm.yml`, `.apm/`          | `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.github/copilot-instructions.md`, `.claude/`, `.cursor/`, `.github/instructions/`, `.agents/`, `.grok/`, `.kiro/`, `.opencode/`, `.windsurf/`, `apm.lock.yaml` |
| How it changes | You write it                | `apm install` / `apm compile` write it                                                                                                                                                                 |
| Committed?     | Yes                         | Yes (so clones have context before anyone runs apm) — but only as regenerated output, never as a manual patch                                                                                          |

`apm_modules/` is a third category: a rebuildable package cache, gitignored automatically, never edited or committed.

## How to tell if a specific file is generated

- **Root context files** (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.github/copilot-instructions.md`) carry a first-line
  HTML comment marker, e.g. `<!-- Generated by APM CLI -->` or `<!-- Generated by APM CLI from .apm/ primitives -->`. If
  the marker is there, it's generated — edit the source instead. If a file like `CLAUDE.md` exists with **no** marker,
  it's hand-authored on purpose; APM will never overwrite or delete it (`apm compile --clean` explicitly skips
  marker-less files), and it's fine to edit directly.
- **Everything else that mirrors a `.apm/` source** — `.claude/skills/`, `.claude/agents/`, `.cursor/rules/*.mdc`,
  `.github/instructions/*.md`, `.agents/skills/`, per-harness MCP config, etc. — is deployed by `apm install` and should
  be treated as generated even without a marker comment, because a matching source almost certainly exists under
  `.apm/`.
- **`apm.lock.yaml`** is always generated. Never hand-edit it — it's rewritten from the resolution result on every `apm
  install`.
- **`apm_modules/`** is always cache. Never edit or commit it.
- If you're genuinely unsure whether a given file is generated, run `apm audit` — see below.

## What to edit instead, by task

| You want to...                                   | Edit this                                                                          | Then run                                                                                                      |
| ------------------------------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Change a coding standard / guideline             | `.apm/instructions/*.instructions.md`                                              | `apm compile` (and `apm install` — some targets read instructions natively)                                   |
| Add or change a skill                            | `.apm/skills/<name>/SKILL.md`                                                      | `apm install`                                                                                                 |
| Add or change an agent persona                   | `.apm/agents/*.agent.md`                                                           | `apm install`                                                                                                 |
| Add or change a prompt / slash command           | `.apm/prompts/*.prompt.md`                                                         | `apm install`                                                                                                 |
| Add a lifecycle hook                             | `.apm/hooks/*.json`                                                                | `apm install`                                                                                                 |
| Pull in someone else's skill/instructions/plugin | `apm install <owner/repo>[#ref]` — this edits `apm.yml` _and_ installs in one step | (nothing further)                                                                                             |
| Add an MCP server                                | `apm install --mcp <server> --transport <name>`                                    | (nothing further)                                                                                             |
| Remove a dependency                              | Delete the entry from `dependencies.apm:` / `dependencies.mcp:` in `apm.yml`       | `apm install` (prunes the deployed files and lockfile entry automatically — don't hand-delete deployed files) |
| Change which harnesses this repo targets         | `targets:` field in `apm.yml`                                                      | `apm install` and/or `apm compile`                                                                            |

If you edited `apm.yml` by hand instead of via `apm install <pkg>`, that's fine — but the manifest change on its own
does nothing until you run `apm install`.

## After any change to `.apm/` or `apm.yml`

1. `apm install` — deploys skills/prompts/agents/hooks/MCP, regenerates `apm.lock.yaml`.
2. `apm compile` — only needed if the target reads instructions through a root context file rather than natively
   (Claude, Cursor, Codex, Gemini, Grok Build, OpenCode, Windsurf, Kiro all do; Copilot doesn't need it).
3. Commit `apm.yml`, `apm.lock.yaml`, and every changed generated file **together, in the same change**. A manifest
   change committed without the regenerated output is exactly the drift the CI check exists to catch.
4. Never commit `apm_modules/`.

## Sanity-check before finishing

Run `apm audit`. It's cache-only (no network) and reports:

| Finding        | Meaning                                                                    | Fix                                                                    |
| -------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `modified`     | A generated file's content differs from what install/compile would produce | Revert the hand-edit; move the change into the matching `.apm/` source |
| `unintegrated` | A `.apm/` source exists but its deployed counterpart is missing            | `apm install`                                                          |
| `orphaned`     | A deployed file exists with no current source                              | `apm install` (cleans it up)                                           |
| `unrecorded`   | Output matches, but the lockfile doesn't record it                         | `apm install`, then commit the regenerated `apm.lock.yaml`             |

If a task touched anything under "generated output" above, treat a clean `apm audit` as a completion check, the same way
you'd run a linter.

## Command reference

```bash
apm install                    # restore from apm.lock.yaml (no args)
apm install <owner/repo>[#ref] # add a dependency + install, in one step
apm install --dev <pkg>        # add as a devDependency
apm install --mcp <server> --transport <name>   # add an MCP server
apm install --dry-run          # show the plan, write nothing
apm update                     # refresh deps to latest matching versions/refs
apm outdated                   # check what's stale, without changing anything
apm run <script>                # invoke a scripts: entry from apm.yml
apm compile                    # (re)generate root context files (CLAUDE.md etc.)
apm compile --dry-run          # preview compile output, write nothing
apm compile --clean --dry-run  # preview removal of stale generated files
apm audit                      # drift + hidden-Unicode check, cache-only
apm audit --ci                 # stricter variant used in CI gates
apm view <package>             # inspect what a lockfile entry actually shipped
apm list                       # list scripts declared in apm.yml
apm targets                    # preview which harnesses auto-detection resolves to
```

## Don't

- Don't hand-edit `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` / `.github/copilot-instructions.md` when they carry the
  "Generated by APM CLI" marker — edit `.apm/instructions/` and run `apm compile`.
- Don't hand-edit anything under `.claude/`, `.cursor/`, `.github/instructions/`, `.agents/`, or other target-owned
  directories — edit the matching `.apm/` source and run `apm install`.
- Don't hand-edit `apm.lock.yaml`.
- Don't commit `apm_modules/`.
- Don't hand-delete a deployed file to "remove" a skill/instruction — remove the source or the `apm.yml` entry and let
  `apm install` prune it, so the lockfile stays consistent.
- Don't edit `apm.yml` and stop — always follow with `apm install` (and `apm compile` when the target needs it), and
  commit the regenerated output alongside the manifest change.
